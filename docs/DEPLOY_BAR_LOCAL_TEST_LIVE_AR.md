## 2) ما أُضيف في هذه الجولة (نطاق ضيق ووظيفي)

1. **بوابة مراجعة قبل النشر (خادمية نقية):** `server/services/DeployPrepublishGate.ts`
   تُصنِّف نفس الشروط التي يفرضها المنفّذ/الراوت أصلاً (كشجرة العمل النظيفة، SHA كامل،
   فحص الأسرار، التفعيلات، المنطقة، رابط التحقق، إثبات المصدر، أدوات النشر، عزل
   البيانات) إلى 12 بندًا بحالات `ok / blocked / unverified`. البوابة **عرض حالة
   فقط**: لا تمنح صلاحية ولا تتجاوز أي حارس؛ النشر الحقيقي يمر عبر حارسَي
   `DeployRealExecutor`/`DeployExecutor` المفشلَين-مغلقَين كما هي.
2. **أُثرِي بيئة الهدف بـ«الدومين المتوقع»:** `resolveAppHostingHost` في
   `server/config/deployTarget.ts` يُشتق الدومين المتوقع وفق الصيغة المثبتة خارجيًا
   (`backendId--projectId.<region>.hosted.app`)، ويُرجع `null` فشلاً مغلقًا عند غياب
   المنطقة — فلا يُخترع دومين أبدًا.
3. **حالة أغنى في snapshot `/api/admin/deploy/state`:** حقول جديدة على
   `shared/deploySystem.ts`: `deployTarget.location`، `deployTarget.expectedDomain`،
   `dataEnvironment`، `gate`، `tools`. كلها إضافية ولا تكسر أي مستهلك قديم.
4. **كشف أدوات النشر (قراءة فقط):** `server/services/DeployToolsService.ts` يجري
   `firebase --version` محليًا فقط (بلا مشروع/شبكة/توثيق)، مع تخزين مؤقت 5 دقائق
   ومدخل حقن للاختبارات، وفشل مغلق (`available:false`).
5. **حارس نشر أحادي المسار (single-flight):** طلب نشر ثانٍ أثناء سريان الأول
   يُرفض `409 DEPLOY_PUBLISH_IN_PROGRESS` (نفس نمط الاستعادة الموجود). يُضبط الحارس
   تزامنيًا قبل أي `await` ويُفرَّغ في `finally` على كل المسارات.
6. **بطاقة الحالة العربية في الشريط (`src/components/deploy-bar.tsx`):**
   شارة حكم البوابة + 12 بندًا بأسبابها + زر **«فحص ما قبل النشر»** حقيقي متصل
   بـ`POST /api/admin/deploy/checks` (لا أزرار وهمية) + شارات نتائج آخر فحص + بيانات
   الهدف (المشروع/Backend/المنطقة/الدومين المتوقع مع «غير متحقق» عند غيابه) + هوية
   Git (SHA كامل/فرع/شجرة العمل/تطابق GitHub) + شارات القدرات (نشر حقيقي/إنتاج/
   المخزن/بيانات التشغيل/إصدار CLI) + شارة «تحقق بعد النشر: ناجح» على كل إصدار مستقر.

## 5) إعداد LOCAL / TEST / LIVE في الشريط

- **LOCAL (شجرة العمل):** الشريط مرئي فقط لعميل تطوير مبنى على
  `NODE_ENV=development` ولجلسة مسؤول تُقرّها حالة `/api/admin/deploy/state`
  (الحراسة خادمية: `requireSameOrigin + requireAdmin + بوابة DEV`). إخفاؤه في
  الواجهة ليس حارسًا — كل النقاط تُحرس على الخادم.
- **TEST (وجهة النشر المعزولة):** `rwqan-757` / `rwqan-backend`، ثابتة على
  الخادم (`resolveDeployTarget`)، لا تأتي من المتصفح أبدًا. المنطقة:
  `europe-west4`، الدومين المتوقع:
  `https://rwqan-backend--rwqan-757.europe-west4.hosted.app/` (مُثبت من
  `deployTarget.ts:35-37`؛ أي إدخال من العميل غير معتمد). أي مشروع إنتاجي في
  طلب TEST مرفوض (`deployTargetBlockers`).
- **LIVE:** `rwqan-757` / `rwqan` / `https://rwqan.sa` — يبدأ فقط بعد
  `DEPLOY_REAL_DEPLOY=enabled` (لا يوجد تفعيل إنتاجي منفصل بعد 0.3.0)، ويبقى النشر الحي
  مشروطًا بموافقة إدارية صريحة، ومراجعة الدومين المتأثر، وإثبات مصدر البناء من لوحة
  التحكم، ومسبار الوصول. لا يُنشئ 0.4.0 أي Commit تلقائي لـLIVE.

الفروقة الدلالية التي يعرضها الشريط الآن بأسمائها التقنية كما هي: `TEST`/`LIVE`
لبيئة الهدف، و`dataEnvironment` لبيانات التشغيل (تبديل في-الذاكرة يُرجَع إلى TEST
عند إعادة تشغيل الخادم).

## 6) عزل TEST عن LIVE — ما ثبت وما بقي غير متحقق

**الثبت كوديًا (من المصدر الفعلي `deployTarget.ts`):**
- TEST → المشروع `rwqan-757`، backend `rwqan-backend`، المنطقة `europe-west4`،
  الدومين `https://rwqan-backend--rwqan-757.europe-west4.hosted.app/`
  (`deployTarget.ts:35-37`).
- LIVE → المشروع `rwqan-757`، backend `rwqan`، الدومين `https://rwqan.sa`
  (`deployTarget.ts:40-41`).
- TEST وLIVE **يشتركان في نفس المشروع `rwqan-757`**; العزل بينهما على مستوى
  الـ*backend* فقط (`rwqan-backend` مقابل `rwqan`) وليس على مستوى المشروع.
- تحقُّق خارجي سابق (قراءة فقط): الدومين
  `rwqan-backend--rwqan-757.europe-west4.hosted.app` يُعيد HTTP 200، بينما
  quello نفسه في `us-central1` يُعيد 404 — confirming أن `europe-west4` هي
  المنطقة المضبوطة لهذا الخلفية.

**غير متحقق (لا دليل من إعدادات الاستضافة الفعلية بعد):**
| المورد | التصنيف | ما يلزم |
| --- | --- | --- |
| Environment name=`test` للbackend `rwqan-backend` في Firebase Console | غير متحقق | قراءة لوحة تحكم App Hosting (إعدادات الخلفية) |
| سر TEST `rwqan-test-firebase-sa/versions/1` في مشروع `rwqan-757` → project_id | غير متحقق | `gcloud secrets versions access` (مصادقة gcloud منتهية الصلاحية في هذه الجلسة) |
| إعدادات LIVE الفعلية للbackend `rwqan` (أي secret يُستخدم، وهل محدود READ-ONLY في IAM) | غير متحقق | قراءة وحدة التحكم / IAM لمشروع `rwqan-757` |
| عزل فعلي TEST↔LIVE في الاستضافة (أي مشروع، أي Firestore Database لكل backend) | **UNVERIFIED** | دليل من إعدادات الاستضافة الفعلية (الشرط الإلزامي) |

**ملحوظة:** PROJECT `rwqan-sa-dev` / Backend `rwqan-dev-backend` الواردة في نسخ أقدم
من هذا التوثيق تشير إلى تصميم سابق؛ الهدف الحالي لـTEST في الكود هو
`rwqan-757` / `rwqan-backend` conforme لـ`deployTarget.ts`.

لا تُستخدم بيانات LIVE في أي اختبار؛ كل الاختبارات أعلاه in-memory وغير متصلة.

## 7) الوجهة المستقبلية لنشر TEST (وبأي أدلة)

الوجهة في الكود: **`rwqan-757` / `rwqan-backend`**
(`deployTarget.ts:35-37`). الدومين المتوقع (توقّع، لا إثبات):
`https://rwqan-backend--rwqan-757.europe-west4.hosted.app/`.
**بلا أدوات إثبات خارجية، لا يزال نشر TEST غير «جاهز فعليًا»** — هذا التوثيق لا يدّعي
غير ذلك. التسلسل المستقبلي الصحيح:

1. منح الصلاحيات على `rwqan-sa-dev` لِحساب `info@rwqan.sa` (يتطلب موافقتك).
2. قراءة لوحة التحكم قراءة-فقط: Backend الـDEV + منطقه الحقيقي + اتصال GitHub.
3. ضبط `DEPLOY_APP_HOSTING_LOCATION` و`DEPLOY_DEV_BASE_URL` على القيم المُثبتة
   (لا قيم مخترعة) — أو إتاحة قراءتها على الخادم عند التشغيل.
4. من الشريط: اختيار TEST → «فحص ما قبل النشر» → مراجعة البوابة (يجب أن تكون
   «جاهز للمراجعة» بأمانة) → موافقة صريحة.
5. الخادم يتحقق مجددًا (الوجهة/الصلاحيات/الفحوص) ثم ينفّذ عبر
   `firebase apphosting:rollouts:create`، ويلتزم الإصدار **فقط** بعد إثبات هوية
   مصدر البناء من لوحة التحكم + مسبار الوصول. فشل أي خطوة = `failed/502/409`
   وليس نجاحًا.

## 8) حماية LIVE وإجراءات «طلب موافقة منفصلة»

- اختيار LIVE لا ينشر شيئًا؛ محاولات النشر إلى الإنتاج تتوقف إذا لم يكن
  `DEPLOY_REAL_DEPLOY=enabled` أو إذا فشل أي فحص/صلاحية/هدف.
