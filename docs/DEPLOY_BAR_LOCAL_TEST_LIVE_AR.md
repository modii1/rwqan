# RWQAN DEPLOY — شريط النشر الآمن: LOCAL → TEST → LIVE

> هذا توثيق الجولة الأخيرة (بوابة المراجعة قبل النشر + بطاقة الحالة + حماية النشر
> الأحادي). جميع التغييرات في هذا الملف **تعديلات محلية غير مُلتزمة (uncommitted)**
> على فرع `test/unified-gateway-ui-only` — لم يُنفَّذ أي نشر حقيقي، ولا أي تغيير
> سحابي، ولا أي كتابة على قواعد البيانات.
>
> **نتيجة البوابة ثلاثة احتمالات حرفيًا:** «جاهز للمراجعة» / «ممنوع بسبب فشل فحص» /
> «غير متحقق — نقص معلومات أو صلاحيات». لا توجد حالة رابعة، ولا تجاوز لأي فحص
> فاشل، ولا ادّعاء بأن نشر TEST «جاهز فعليًا» قبل إثبات الوجهة والعزل والصلاحيات.

---

## 1) الخلاصة الصريحة

| السؤال | الجواب |
| --- | --- |
| هل تغيّرت ملفات محلية؟ | نعم (غير مُلتزمة — راجع قائمة الملفات أدناه) |
| هل نُفِّذ أي نشر حقيقي؟ | لا — إطلاقًا |
| هل تغيّرت إعدادات سحابية؟ | لا — إطلاقًا |
| هل كُتبت بيانات إلى قواعد بيانات؟ | لا (الاختبارات كلها in-memory فقط) |
| هل أُثبت عزل TEST عن LIVE بالكامل؟ | **لا — لم يكتمل** (تفاصيل العزل في القسم 6) |

## 2) ما أُضيف في هذه الجولة (نطاق ضيق ووظيفي)

1. **بوابة مراجعة قبل النشر (خادمية نقية):** `server/services/DeployPrepublishGate.ts`
   تُصنِّف نفس الشروط التي يفرضها المنفّذ/الراوت أصلاً (كشجرة العمل النظيفة، SHA كامل،
   فحص الأسرار، التفعيلات، المنطقة، رابط التحقق، إثبات المصدر، أدوات النشر، عزل
   البيانات) إلى 12 بندًا بحالات `ok / blocked / unverified`. البوابة **عرض حالة
   فقط**: لا تمنح صلاحية ولا تتجاوز أي حارس؛ النشر الحقيقي يمر عبر حارسَي
   `DeployRealExecutor`/`DeployExecutor` المفشلَين-مغلقَين كما هي.
2. **أُثرِي بيئة الهدف بـ«الدومين المتوقع»:** `resolveAppHostingHost` في
   `server/config/deployTarget.ts` يُشتق الدومين المتوقع وفق الصيغة المثبتة خارجيًا
   (`backendId--projectId.<region>.hosted.app`)، ويُرجع `null` فشلاً مغلقًا عند غياب
   المنطقة — فلا يُخترع دومين أبدًا.
3. **حالة أغنى في snapshot `/api/admin/deploy/state`:** حقول جديدة على
   `shared/deploySystem.ts`: `deployTarget.location`، `deployTarget.expectedDomain`،
   `dataEnvironment`، `gate`، `tools`. كلها إضافية ولا تكسر أي مستهلك قديم.
4. **كشف أدوات النشر (قراءة فقط):** `server/services/DeployToolsService.ts` يجري
   `firebase --version` محليًا فقط (بلا مشروع/شبكة/توثيق)، مع تخزين مؤقت 5 دقائق
   ومدخل حقن للاختبارات، وفشل مغلق (`available:false`).
5. **حارس نشر أحادي المسار (single-flight):** طلب نشر ثانٍ أثناء سريان الأول
   يُرفض `409 DEPLOY_PUBLISH_IN_PROGRESS` (نفس نمط الاستعادة الموجود). يُضبط الحارس
   تزامنيًا قبل أي `await` ويُفرَّغ في `finally` على كل المسارات.
6. **بطاقة الحالة العربية في الشريط (`src/components/deploy-bar.tsx`):**
   شارة حكم البوابة + 12 بندًا بأسبابها + زر **«فحص ما قبل النشر»** حقيقي متصل
   بـ`POST /api/admin/deploy/checks` (لا أزرار وهمية) + شارات نتائج آخر فحص + بيانات
   الهدف (المشروع/Backend/المنطقة/الدومين المتوقع مع «غير متحقق» عند غيابه) + هوية
   Git (SHA كامل/فرع/شجرة العمل/تطابق GitHub) + شارات القدرات (نشر حقيقي/إنتاج/
   المخزن/بيانات التشغيل/إصدار CLI) + شارة «تحقق بعد النشر: ناجح» على كل إصدار مستقر.

## 5) إعداد LOCAL / TEST / LIVE في الشريط

- **LOCAL (شجرة العمل):** الشريط مرئي فقط لعميل تطوير مبنى على
  `NODE_ENV=development` ولجلسة مسؤول تُقرّها حالة `/api/admin/deploy/state`
  (الحراسة خادمية: `requireSameOrigin + requireAdmin + بوابة DEV`). إخفاؤه في
  الواجهة ليس حارسًا — كل النقاط تُحرس على الخادم.
- **TEST (وجهة النشر المعزولة):** `rwqan-sa-dev` / `rwqan-dev-backend`، ثابتة على
  الخادم (`resolveDeployTarget`)، لا تأتي من المتصفح أبدًا. أي مشروع إنتاجي في
  طلب TEST مرفوض (`deployTargetBlockers`).
- **LIVE:** `rwqan-757` / `rwqan-backend` / `rwqan.sa` — لا يبدأ إلا بتفعيلين
  صريحين منفصلين (`DEPLOY_REAL_DEPLOY=enabled` ثم `DEPLOY_ALLOW_PRODUCTION=enabled`)
  مع `NODE_ENV=development`، ويبقى النشر الحي مشروطًا بموافقة إدارية صريحة، ومراجعة
  الدومين المتأثر، وإثبات مصدر البناء من لوحة التحكم، ومسبار الوصول.

الفروقة الدلالية التي يعرضها الشريط الآن بأسمائها التقنية كما هي: `TEST`/`LIVE`
لبيئة الهدف، و`dataEnvironment` لبيانات التشغيل (تبديل في-الذاكرة يُرجَع إلى TEST
عند إعادة تشغيل الخادم).

## 6) عزل TEST عن LIVE — ما ثبت وما بقي غير متحقق

**الثبت خارجيًا (قراءة فقط عبر Firebase CLI، `info@rwqan.sa`) في 2026-10-26:**
- الإنتاج الحقيقي: المشروع `rwqan-757` (رقم `371865284292`) يضم backend فعليين في
  `europe-west4`:
  - `rwqan-backend` — دومينه `rwqan-backend--rwqan-757.europe-west4.hosted.app`
    وهو **بالضبط** الدومين الذي يذكره المستخدم → إذَن هذا الدومين **إنتاجي وليس
    TEST**، وقد أُثبت ذلك من لوحة التحكم (اتصال GitHub `modii1-rwqan`، آخر تحديث
    2026-10-25 23:05Z).
  - `rwqan` — متصل بـ`iheeb1/rwqan-sa` (يطابق `firebase.json`).

**غير متحقق (صادقون حتى جديد الأدلة):**
| المورد | التصنيف | ما يلزم |
| --- | --- | --- |
| مشروع `rwqan-sa-dev` | غير ظاهر في `projects:list` (رفض 403 على استعلامه) | منح الحساب `serviceusage.serviceUsageConsumer` + قراءة App Hosting على الأقل |
| Backend الـDEV `rwqan-dev-backend` | بلا أدلة | قراءة لوحة تحكم App Hosting لمشروع DEV |
| منطقة Backend الـDEV (التوثيق القديم يدّعي `me-central2` — لم يُثبت) | غير متحقق | نفس الاستعلام |
| Firestore/Storage/Secrets في `rwqan-sa-dev` | غير متحقق | جرد قراءة-فقط بعد منح الصلاحيات |
| القيم في `.env.development.local` (المنطقة/الرابط/الأعلام) | غير مقروءة عمدًا (سياسة عدم قراءة الأسرار) | التطبيق يُقرأ في وقت التشغيل (الواجهة تعرض `غير متحقق` حيثما ينقص) |

لا تُستخدم بيانات LIVE في أي اختبار؛ كل الاختبارات أعلاه in-memory وغير متصلة.

## 7) الوجهة المستقبلية لنشر TEST (وبأي أدلة)

الوجهة في الكود: **`rwqan-sa-dev` / `rwqan-dev-backend`**
(`deployTarget.ts:33-34`). الدومين المتوقع عند ضبط المنطقة (توقّع، لا إثبات):
`https://rwqan-dev-backend--rwqan-sa-dev.<region>.hosted.app`.
**بلا أدوات إثبات خارجية، لا يزال نشر TEST غير «جاهز فعليًا»** — هذا التوثيق لا يدّعي
غير ذلك. التسلسل المستقبلي الصحيح:

1. منح الصلاحيات على `rwqan-sa-dev` لِحساب `info@rwqan.sa` (يتطلب موافقتك).
2. قراءة لوحة التحكم قراءة-فقط: Backend الـDEV + منطقه الحقيقي + اتصال GitHub.
3. ضبط `DEPLOY_APP_HOSTING_LOCATION` و`DEPLOY_DEV_BASE_URL` على القيم المُثبتة
   (لا قيم مخترعة) — أو إتاحة قراءتها على الخادم عند التشغيل.
4. من الشريط: اختيار TEST → «فحص ما قبل النشر» → مراجعة البوابة (يجب أن تكون
   «جاهز للمراجعة» بأمانة) → موافقة صريحة.
5. الخادم يتحقق مجددًا (الوجهة/الصلاحيات/الفحوص) ثم ينفّذ عبر
   `firebase apphosting:rollouts:create`، ويلتزم الإصدار **فقط** بعد إثبات هوية
   مصدر البناء من لوحة التحكم + مسبار الوصول. فشل أي خطوة = `failed/502/409`
   وليس نجاحًا.

## 8) حماية LIVE وإجراءات «طلب موافقة منفصلة»

- اختيار LIVE لا ينشر شيئًا؛ محاولات النشر إلى الإنتاج تتوقف بلا التفعيل الثاني.
- طلب TEST لا يمكنه استنساخ وجهة الإنتاج؛ `deployTargetBlockers` في TEST يرفض
  مشروع الإنتاج (مُختبَر)، والمنفّذ يرفض أي هدف لا يطابق الثابت للبيئة.
- الاستعادة محصورة في بيئة النشر المستهدفة نفسها، ولا تمس قواعد البيانات أبدًا،
  ولا يمكنها استهداف Backend آخر (كل الاستعادات تكوّن rollout للهدف الثابت).
- **عناصر تنتظر موافقتك الصريحة المنفصلة (لم يُنفَّذ أي منها):**
  1. منح صلاحيات IAM على `rwqan-sa-dev` (قراءة).
  2. إنشاء/تأكيد Backend DEV وضبط منطقته.
  3. أي نشر حقيقي إلى TEST أو LIVE.
  4. أي تغيير IAM/Secrets/دومينات/ربط `rwqan.sa`.

## 9) كيف تشغّل الشريط محليًا

1. فرع العمل: `test/unified-gateway-ui-only` (التعديلات غير مُلتزمة — راجعها
   وألتزمها بنفسك؛ لا سجل قيم أسرار في السجلات).
2. شغّل خادم التطوير المعتمد في المستودع. يجب أن يكون
   `NODE_ENV=development` وكانت جلسة مسؤول بنفس الأصل (same-origin).
3. الشريط يظهر أعلى كل صفحة: «نشر» / مبدّل `LIVE|TEST` للبيانات / «استعادة».
   عند فتح اللوحة توجد بطاقة الحالة (البوابة + الهدف + Git + الفحوص + القدرات)
   وزر «فحص ما قبل النشر» الحقيقي.
4. يمكنك إعادة تشغيل مجموعات الفحص بأمر القسم 4 لتأكيد المطابقة.

## 10) مخاطر/قيود متبقية

- عزل TEST لم يُثبت بالكامل بعد (قسم 6) — البوابة تعرض «غير متحقق» بدل ادعاء.
- بند `admin_permissions` في البوابة يثبت حراسة الجلسة/الأصل لطريقة الحالة فقط؛
  الصلاحيات العميقة لكل عملية تُفرض في مساراتها (كما كانت) وليست إثباتًا من البوابة.
- كشف GitHub يبقى إرشاديًا (الحكم لا يعتمده) لأن rollout يُبنى من SHA المحلي
  ويُثبت ما يُخدَم من لوحة التحكم لاحقًا.
- فحص TypeScript داخل طلبات HTTP يبقى NOT_RUN بطيءًا عمدًا (يُشغَّل من زر
  «فحص ما قبل النشر» خارج الطلب مثلما كانت المرحلة E).
- عدم الالتزام: كل تعديلات هذه الجولة غير ملتزمة؛ لا شيء يصل إلى GitHub/Google
  حتى تلتزمها وتدفعها بنفسك.
