## 3) كيفية الربط الآمن بـ GitHub (تصميم مقترح)

الهدف: «حفظ الإصدار في GitHub» يعمل بأمان دون تخزين أسرار في المستودع/المتصفح، ودون تنفيذ أوامر
`git` عشوائية من الواجهة.

**المبادئ:**
1. كل عمليات Git تُنفَّذ **على الخادم فقط**، عبر قائمة أوامر مسموحة ثابتة (allow-list)، لا عبر تمرير
  أوامر من الواجهة.
- أوامر مسموحة فقط: `git fetch`, `git rev-parse`, `git status --porcelain`, `git diff --stat`,
  `git tag`, `git push` لمرجع **محدد مسبقًا** (فرع إصدار/وسم). يُرفض أي شيء آخر.
- منع تنفيذ أوامر عشوائية: لا `spawn(shell:true)`، ولا استقبال أي وسيط من المتصفح يدخل في سطر أمر.
- المصادقة مع GitHub: عبر **Secret Manager/Runtime secret** (Personal Access Token أو GitHub App)
  يُقرأ على الخادم فقط، ولا يُرسل للمتصفح ولا يُسجَّل. (غير موجود حاليًا — يحتاج موافقة + إعداده ضمن
  أي مسار CI/CD أو خادم).
- حفظ الإصدار = إنشاء **وسم Git (tag)** مرتبط بـ commit معتمد + (اختياريًا) GitHub Release، على فرع
  إصدار مخصص. تُرفض الفروع/الـ commits غير المعتمدة عبر allow-list (مثل حصر النشر بالفرع
  `release/rwqan-test` أو `main` بعد موافقة).
- **تمييز صريح** في الواجهة والسجل بين: «حُفظ في GitHub» و«نُشر إلى الموقع» — عمليتان منفصلتان،
  ونجاح إحداهما لا يعني الأخرى.

> حالة GitHub الحالية للربط (هل App Hosting مرتبط بـ GitHub أم لا، وأي فرع): **UNKNOWN** — يتطلب
> تحقّقًا بصلاحية قراءة قبل البناء. لا نخمّن.

## 4) آلية الإصدارات الخمسة والاستعادة

### 4.1 نموذج البيانات المقترح (سجل الإصدارات)
مجموعة Firestore جديدة في DEV (اسم مقترح: `deploy_releases`) بحقول غير حساسة:
`releaseId` (فريد)، `version` (MAJOR.MINOR.PATCH)، `environment` (`TEST`/`LIVE`)، `gitCommit`,
`gitTag`, `gitBranch`, `sourceRepoUrl`, `createdAt`, `createdBy` (هوية إدارية)،
`status` (`draft|validated|saved_to_git|deploying|deployed|failed|rolled_back`)،
`checks: { tsc, tests, build, secretScan, postDeployHealth }` (PASS/FAIL + ملخص)،
`deployTarget` (اسم Backend/البيئة)، `rolloutRef` (مرجع النشر)، `artifactsHash`.
**ممنوع** تخزين أي سر في هذا السجل.

سجل تدقيق منفصل (اسم مقترح: `deploy_audit_log`) غير قابل للتعديل: `at`, `actorRole:'admin'`,
`action`, `releaseId`, `result`, `reason` — بلا أسرار.

### 4.2 مسار النشر (زر «نشر») — خطوات إلزامية بالتسلسل
1. **فحص Git:** `git status --porcelain` / `git diff --stat` + فحص أن لا ملفات أسرار/غير مصرّح بها
   ضمن التغيير (رفض `.env*`, `*.pem`, `*.key`, مفاتيح معروفة). إيقاف عند أي اشتباه.
2. **فحوص إلزامية:** `tsc --noEmit` + المجموعة المطلوبة من الاختبارات + `next build ...`.
   **لا تجاوز تلقائيًا لأي فشل** — الإيقاف فوري.
3. **توليد إصدار فريد** + سجل تغييرات + نتائج الفحوصات.
4. **حفظ في GitHub** (وسم/فرع معتمد) عبر المسار الآمن (بند 3). حالة منفصلة عن النشر.
5. **أثر نشر قابل للتتبع** وربط الإصدار بمصدره (commit/tag).
6. **النشر عبر CI/CD** إلى البيئة الصحيحة (لاحقًا فقط، وبموافقة؛ ممنوع الآن).
7. **فحوص ما بعد النشر** وتسجيل النتيجة.
8. **إيقاف/استعادة** عند فشل فحص الصحة.

> في المرحلة الحالية: 1–3 قابلة للتنفيذ في DEV بأمان؛ 4–8 تتطلب قرارات (GitHub token، مسار CI/CD،
> بيئة نشر） ولا تُنفَّذ أثناء بناء النظام.

### 4.3 الاستعادة (زر «استعادة»)
- عرض **آخر 5 إصدارات منشورة بنجاح على الأقل** (رقم، تاريخ، مصدر Git، نتائج فحوص ما بعد النشر).
- معاينة الإجراء قبل التنفيذ (diff/ملخص). الاستعادة إلى الإنتاج تتطلب **تأكيدًا صريحًا + صلاحية إدارية**.
- استعادة **إصدار التطبيق وإعداداته المتوافقة فقط**؛ **لا استعادة تلقائية لقاعدة البيانات**.
- التحقق من توافق تغييرات DB مع الإصدار السابق (رفض الاستعادة إن كان التغيير غير متوافق).
- رفض استعادة إصدار **غير مكتمل** أو **مجهول المصدر** (بلا commit/tag).
- سجل تدقيق دائم لكل نشر/استعادة.

**آلية الاستعادة الفعلية في App Hosting** (Rollout مرتبط بـ Build سابق أو commit سابق): **UNKNOWN**
حتى التحقق. بديل معتمد مبدئيًا: إنشاء Rollout جديد مثبّت على الإصدار السابق — يُثبَت في المرحلة E.

## 5) فصل TEST وLIVE

### 5.1 المطلوب من النظام
- **TEST:** موارد DEV المعزولة (Firebase `rwqan-sa-dev`, R2 `rwqan-sa-dev`), مفاتيح اختبار الدفع/الرسائل,
  مخزن تجريبي, بيانات وهمية, ضمان أن لا مجدول/Webhook يصل للإنتاج.
- **LIVE:** اتصال **مضبوط** بموارد الإنتاج **للقراءة/المعاينة فقط افتراضيًا**؛ مفاتيح الإنتاج من مخزن
  أسرار على الخادم فقط؛ لا نسخ أسرار للإنتاج إلى ملفات DEV/المستودع/المتصفح؛ فصل صلاحية قراءة
  الإنتاج عن صلاحية تعديله؛ منع الكتابة على الإنتاج إلا بصلاحية منفصلة + تأكيد صريح؛ عدم تغيير قاعدة
  بيانات/إعدادات الموقع الحقيقي عند تبديل المفتاح.

### 5.2 هل تدعم البنية الحالية هذا الفصل بأمان؟
**لا (حاليًا).** الأسباب المثبتة:
- مصدر الاعتماد الواحد `FIREBASE_SERVICE_ACCOUNT` (`server/config/firebase.ts:12`) يمنح **قراءة+كتابة**
  عبر Admin SDK في نفس العملية، لا تمييز للقراءة فقط.
- `loadEnv.ts` يحمّل ملفًا واحدًا؛ لا يوجد تجريد لـ«مفتاح البيئة» ولا اعتماد ثانٍ.
- `requireAdmin` ثنائي بلا نطاق.
- تبديل المفتاح ضمن العملية نفسها قد يمسّ الإنتاج (لا فصل فعلي على مستوى التنفيذ).

### 5.3 التصميم الآمن المقترح (بدون اتصال إنتاجي غير آمن)
- **مفتاح البيئة (TEST/LIVE)** = مفتاح **واجهة/جلسة** يحدّد *سياق العرض* فقط، لا يبدّل اعتماد العملية.
- LIVE **قراءة فقط** يتطلب **اعتمادًا منفصلًا للقراءة** يُخزَّن على الخادم (خارج المستودع/المتصفح)،
  ويُحمَّل بشكل كسول عند طلب المعاينة، مع طبقة استدعاء **مقيّدة بالقراءة فقط** (لا `set/update/delete`).
- في المرحلة B–E: عند غياب اعتماد LIVE آمن → الوضع LIVE يبقى **معطّلًا** ويُوثّق الحاجز، **ولا يُنفَّذ
  اتصال غير آمن**. (التزامًا بشرطك: «إذا كانت البنية لا تدعم الفصل بأمان، وثّق ولا تنفّذ».)

> الخلاصة: TEST قابل للبناء الآن بالكامل على موارد DEV. LIVE للمعاينة **مبدأيًا معطّل** حتى توفير
> اعتماد قراءة إنتاجي منفصل + موافقتك، وسيُوثَّق كحاجز صريح.

## 8) مراحل التنفيذ واختبارات القبول

### المرحلة A — فحص وتوثيق (هذه المرحلة) ✅
- **المخرج:** هذا المستند. **اختبار القبول:** لا تغييرات كود/نشر؛ توثيق يستند لملفات فعلية؛ كل
  مجهول مُوسَم UNKNOWN.

### المرحلة B — تصميم الواجهة + نموذج البيانات والصلاحيات + بيئة وهمية
- تصميم الشريط وقسم الإدارة (DEV فقط)، نموذج `deploy_releases` + `deploy_audit_log`، وضبط حدود
  `/api/admin`. بناء "mock/fake" للتجربة بلا نشر حقيقي.
- **اختبارات القبول:** الاختبارات تُثبت أن واجهات DEPLOY كلها 401/403 بلا جلسة إدارية؛ لا يظهر
  الشريط لغير الأدمن؛ لا أسرار في أي استجابة/سجل؛ نموذج البيانات يرفض الحقول السرّية.

### المرحلة C — سجل الإصدارات + التحقق + تكامل GitHub في DEV (مكتملة جزئيًا)
- تنفيذ `DeployReleaseStore` + فحوص Git/الأسرار + تشغيل `tsc/الاختبارات/البناء` + طبقة Git المقيّدة.
- **اختبارات القبول:** رفض الأسرار؛ إيقاف عند فشل فحص؛ إنشاء إصدار فريد؛ حالتا «محفوظ في GitHub»
  و«منشور» مستقلتان وعُرضتا بوصفهما مستقلتين؛ منع أمر Git غير مسموح؛ منع نشر متزامن متعارض.
- **ما نُفِّذ فعليًا (المرحلة C):** مخزن Firestore دائم في DEV + سجل تدقيق + فحوص قراءة فقط
  (Git + أسرار) + حفظ سجل عند «نشر» + عرض آخر 5 عند «استعادة»، بفشل-مغلق ولاحفظ فعلي في GitHub
  ولا نشر. التفاصيل: `docs/DEPLOY_SYSTEM_PHASE_C_AR.md`. (الكتابة الفعلية في GitHub مؤجّلة.)

### المرحلة D — استعادة إصدار التطبيق واختبارها محليًا
- عرض آخر 5 إصدارات، معاينة الاستعادة، تأكيد صريح، رفض الإصدار المجهول/غير المكتمل، منع استعادة DB.
- **اختبارات القبول:** سيناريوهات استعادة (نجاح/رفض/تعارض DB) بأدلة؛ سجل تدقيق كامل بلا أسرار.

### المرحلة E — مسار نشر تجريبي إلى بيئة معزولة والتحقق منه
- تنفيذ نشر تجريبي + فحوص ما بعد النشر + آلية إيقاف/استعادة.
- **اختبارات القبول:** نشر تجريبي ناجح مع أثر قابل للتتبع، وفحوص صحة PASS، ونجاح إيقاف/استعادة عند
  الفشل المحاكى. (يتطلب قرار بيئة معزولة + اعتماد GitHub.)

### المرحلة F — خطة منفصلة للاعتماد النهائي إلى `rwqan.sa`
- خطة مستقلة بعد مراجعة أمنية + موافقة صريحة. لا تنفيذ إنتاجي قبلها.

## 10) الخلاصة والتوصية

- كشف الفحص أن المشروع يُنشر حاليًا عبر **Firebase App Hosting** لمشروع الإنتاج `rwqan-757`
  (`apphosting.yaml`, `firebase.json`, `.firebaserc`)، **دون** سجل إصدارات ولا CI/CD في المستودع،
  ومع **افتراضي هدف الإنتاج** (`.firebaserc`) — وهو أخطر نقطة ينبغي حوكمتها أولًا.
- الأساس الأمني المطلوب لنظام DEPLOY **موجود جزئيًا**: حدّ `/api/admin` + `requireSameOrigin` +
  `requireAdmin`، وبوابات عزل DEV. لكن **لا** نموذج أدوار، **لا** فصل قراءة/كتابة للإنتاج، و**لا**
  اعتماد ثانٍ للقراءة، ولا سجل إصدارات — وهي العناصر التي سيُبنى عليها لاحقًا.
- **التوصية:** المضي إلى **المرحلة B** (تصميم + نموذج بيانات + بيئة وهمية) فور موافقتك، مع إبقاء
  LIVE **معطّلًا** حتى توفير اعتماد قراءة إنتاجي منفصل، وعدم أي عمل إنتاجي.

**تحديث الحالة:** اكتملت **المرحلة B** (`docs/DEPLOY_SYSTEM_PHASE_B_AR.md`) ثم **المرحلة C**
(`docs/DEPLOY_SYSTEM_PHASE_C_AR.md`). **أوقف هنا بانتظار موافقتك قبل بدء المرحلة D.**
